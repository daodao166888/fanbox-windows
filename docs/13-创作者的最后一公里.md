# 13 · 创作者的最后一公里

版本 v1.0 · 2026-07-25 · 起因：把 huasheng_editor 的排版与复制能力做进 FanBox

---

## 一、先说清楚问题是什么

花叔写一篇公众号文章，今天的真实链路：

```
即刻/网页/公众号存档  →  素材 md          （agent + skill 干的）
Claude Code 写初稿    →  项目里的 md      （agent 干的）
生图 skill 配图       →  配图/*.png       （agent 干的）
subagent 审校         →  改过的 md        （agent 干的）
────────────────────────────────────────  以上都在 FanBox 里看得见
切浏览器 → 开排版器 → 粘 md → 选样式 → 点复制 → 切公众号后台 → 粘贴
                                            以上全是手指头的活
```

前面四步 agent 全包了，最后一步却要人切三个窗口。**一篇文章从「写完」到「躺进公众号后台」的所有工作量，现在几乎都堆在这最后一公里上。**

这条链路上还有几个更隐蔽的断点：

- 一稿多投时，X / B站 / 小红书各要一次同样的手工搬运
- 商单交付要给品牌方飞书文档，得再手动贴一遍
- 发之前想知道字数、想拿封面图，都要另开工具

## 二、一个判断：FanBox 不是编辑器，是验收台

先否掉一个诱人的方向：把 FanBox 做成写作工具。不做。它拼不过 Ulysses 的写作体验，也不需要拼——**花叔的字不是自己敲的，是 agent 写的。**

FanBox 真正的身份是 agent 产出物的验收台。它已经为代码类产出做好了验收：

| 产出 | 验收方式 | FanBox 已有 |
|---|---|---|
| 代码 | 看 diff、跑起来 | git 改动视图、HTML iframe 预览 |
| 文章 | 看读者眼里的样子 | ← 这一格之前是空的 |

排版档就是补这一格。它不是「加了个排版功能」，是把文章类产出的验收补齐——**读者视角**。作者视角（源码、富文本）看的是字对不对，读者视角看的是这篇东西发出去长什么样。这两件事必须都在你刚让 agent 改完稿的地方发生，否则就要切窗口，一切窗口就断了。

由此得到一条职责边界，后面所有取舍都从它推出来：

> **脑子的活归 agent 和 skill，手指头的活归 FanBox，FanBox 把手指头的活压到零。**

选题、改写、审校、配图，这些是脑子的活，FanBox 一律不碰。搬运、粘贴、切窗口、格式转换，这些是手指头的活，FanBox 全包。

## 三、核心抽象：「去向」

一个 md 文件在预览里躺着，它下一步能去哪？这个问题的答案集合，就是「去向」。

去向不是一个插件系统，也不该长成一面按钮墙。它是一个短到能一眼看完的清单——短，是设计约束，不是妥协。今天这个清单只有两项（公众号、X），未来最多七八项。任何一项要进这个清单，都得先回答：**它省掉了几次切窗口？**

去向按实现方式分三层，这个分层决定了 FanBox 背多少复杂度：

**第一层 · 内建剪贴板**（已完成）
公众号、X。产物是剪贴板里的富文本，零网络、零凭证、零依赖。粘贴动作留给用户——这是权力边界，FanBox 永远不代替人点发送。

**第二层 · 内建导出**（未做）
长图、PDF、纯净 HTML。产物是磁盘上的文件，同样零网络零凭证。

**第三层 · 借道 agent**（未做，但这是 FanBox 独有的一手）
飞书文档、渡口投稿（X Articles / B站专栏）、知识星球。

这些去向都需要第三方登录态和 API。常规做法是在 FanBox 里内建 SDK、存 token、维护 OAuth——那会让一个「本地、零配置、无账号」的工具背上一整套凭证管理责任，且每个平台改一次 API 就得发一次版。

FanBox 不必这么干，因为它右边就有一个终端，终端里就有 agent，agent 手上就有 skill。**「送到飞书」这件事，FanBox 要做的不是实现它，而是把一句命令递到终端里。**

```
[送去…] → 飞书文档
   ↓
终端里出现（可见、可改、由用户回车）：
   用 lark-doc 把 ./稿子.md 发成飞书文档，发完把链接贴回来
```

这一手的收益：

- FanBox 不碰任何第三方凭证，`本地优先、无账号` 的承诺一寸不退
- 去向能力随 skill 生态自动生长，不用发版
- 过程可见——这正是 FanBox 的产品哲学（看清 agent 干的每一件事），而不是黑箱代发
- 命令是明文的，用户随时能改、能拒

代价也要说清楚：这一层依赖终端里有活着的 agent、且装了对应 skill。做法是灰掉不可用项，鼠标移上去一句话说明缺什么，而不是点了没反应。

## 四、已经做了什么（v1，2.9.0）

md 编辑器的第四档：`富文本 / 阅读 / 源码 / 排版`。

- 20 套主题，来自 editor.huasheng.ai，`public/typeset-styles.js` 与上游同源，可整文件覆盖更新
- **预览即产物**：排版档里看到的 HTML 就是粘出去的 HTML，不存在「预览好看、粘过去变样」
- 复制到公众号：全内联样式 + 本地/远程图片转 base64 + 连续多图排成表格网格 + 带底色主题补 section + 引用块适配微信深色模式
- 复制到 X：按 X Articles 白名单清洗，代码块与表格退成引用块保住内容，图片留占位
- 外链图片被浏览器同源策略挡住时，由本机服务代抓（`/api/img-proxy`），图床里的图也能内联进去
- **「送去…」菜单接通第三层**：公众号是主战场，主动作外露一键直达；其余去向收进菜单——「复制到 X」走内建剪贴板，飞书文档 / X Articles·渡口 / B站专栏·渡口把明文指令递给终端里的 agent。只粘不回车；当前标签是裸 shell 就拦下并提示先启动 agent
- **「x 字 · 约 y 分钟」**：按排好版的可见文字算，中文按字英文按词，和公众号后台一个数法

## 五、路线图

排序原则只有一条：**按「省掉几次切窗口」排，不按实现难度排。**

P1 已于 2.9.0 随第一版一起落地（去向菜单 + 字数）。「封面图一键取」评估后砍掉——见第六节。

### P2 · 一稿多投的其余出口

**4. 导出长图**
小红书、朋友圈、即刻要的是图不是文。把排好版的文章切成长图（或按小节切多图）落盘。纯前端 canvas 能做，零依赖。

**5. 导出 PDF**
商单交付、课程讲义要的是 PDF。走系统打印链路，不引第三方库。

### P3 · 值得做但要再想想

**6. 发布前体检**
图裂没有、链接死没死、错别字、行内代码有没有忘了闭合。这是 agent 擅长的活，可以借道第三层：点一下，终端里 agent 跑一遍体检回报。
存疑之处：它跨过了「脑子的活 vs 手指头的活」那条线。倾向做成第三层的一个去向，而不是 FanBox 内建的检查器。

**7. 反向入口：链接抓成本地 md**
粘一个公众号/网页链接进 FanBox，抓成本地 md + 图片（渡口 skill 已具备）。
存疑之处：这违反了「文件在场才有去向」的前提——FanBox 是从文件出发的工具，不是从链接出发的工具。真要做，也该在终端里对 agent 说，而不是在 FanBox 里加一个输入框。

## 六、明确不做的

这份清单和路线图一样重要。

- **不做写作编辑器**。不加字数目标、专注模式、双栏预览、大纲面板。字是 agent 写的。
- **不做发布**。所有去向都停在「剪贴板里 / 磁盘上 / 编辑页已打开」，最后那一下永远由人来点。这条与渡口的边界完全一致。
- **不做样式自定义面板**。不给调字号、配色、间距。主题是选出来的不是调出来的；要新主题就改 `typeset-styles.js` 或提 PR。给 20 个滑杆等于把排版器的坑原样搬进来。
- **不做云、不做账号、不存第三方凭证**。这是第三层「借道 agent」存在的全部理由。
- **不做多平台内容改写**。「把这篇改成小红书语气」是脑子的活，是 agent 和 skill 的活，不是一个按钮的活。
- **不做封面图一键取**（2026-07-26 评估后砍掉）。公众号封面在真实流程里是单独挑、单独生成的，不是「正文第一张图」，一个猜错一半的按钮不如没有。

## 七、怎么算做成了

一句话验收：

> 一篇文章从 agent 写完到躺进公众号后台，中间不切窗口、不做第二次复制粘贴。

2.9.0 之后的距离：发公众号是切 1 次窗口（后台）、复制 1 次（正文）；发 X / B站 / 飞书是 0 次切窗口——指令递进终端，agent 去开页面填内容，人只按最后一下。

那最后一下不可能再少，因为发布权在人手里。这是设计，不是欠债。
